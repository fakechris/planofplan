## 4. decode 速度(输出 tok/s)

严格口径(流 ≥1s 且输出 ≥50 tok,n=15425):

- **均值 155 / p50 149 / p90 207 / p99 253 / 峰值 720 tok/s**
- 按天:132-174 区间波动,16 天内无退化趋势(08-21 偏慢是 vision 模型占比)
- 分时段:全天平稳在 145-165,**无明显高峰降速**(服务端负载对单流速度影响小)
- >300 tok/s 的样本全是亚秒短流(计时粒度噪声),不代表真实吞吐

**结论:v4-flash 单流 decode 稳定在 ~150 tok/s(中位),长期一致。**

## 5. prefill 速度(TTFT 反推)

TTFT(step/start → 首 chunk,含排队+网络):均值 2.88s / p50 2.23s / p90 4.68s。

按非缓存输入规模分桶(输入越大,TTFT 越由 prefill 主导):

| 输入规模 | prefill p50 | p90 | n |
|---|---|---|---|
| 5k-20k | 4.9k tok/s | 10.2k | 380 |
| 20k-50k | 17.1k | 28.9k | 11 |
| 50k-200k | 15.8k | 24.5k | 17 |
| **≥200k** | **18.4k** | **58k** | 40 |

**结论:真实 prefill 吞吐 ≈ 16-20k tok/s(大 prompt 时),峰值 ~60-80k;**
小 prompt 的 TTFT 被 ~2s 固定延迟(排队/路由/网络)主导,不能用小输入
桶的"4.9k"当 prefill 带宽。cache 命中部分不参与 prefill 计算,百万级
上下文靠命中才做到 2-3s 首 token。

## 6. 用真实会话形态重算"本地 vs 云端"(修正第 5 节的抽象假设)

重扫(会话按完整路径分组,131 个会话 / 20,332 步)后的真实负载形态:

| 真实画像 | p50 | p90 | max |
|---|---|---|---|
| 会话冷启动(首 prompt) | **23.8k** | 30.4k | 55.2k |
| 会话峰值上下文 | 100k | 590k | **792k**(13 个会话 >600k) |
| 每轮增量(非缓存 prefill) | **181 tok** | 854 | 702k(compaction 步) |
| 云端 TTFT | 2.23s | 4.68s | 96s |

云端 TTFT 回归(真实增量,n=1343):TTFT = 1.66s + 增量/21.7k tok/s
——1.66s 是排队/网络,21.7k 与分桶估的 16-20k 互证。

**关键修正:"1M 冷启动"在真实负载里不存在。** 会话从 ~24k 起步(系统提示
+工作区),上下文是中途长出来的;最大会话 1451 步:24k→710k 涨 5 个
阶段,一次 compaction 回到 110k,再涨回 389k。每轮增量中位只有 181 tok。

同负载搬 M5 Ultra(2k prefill / 90 decode / KV 136KB/tok):

| 指标 | 云端实测 | 本地(同负载) |
|---|---|---|
| 稳态每轮 TTFT | 2.23s(p90 4.68) | **0.16s(p90 0.76)**——本地反超 14×(KV 常驻,无排队) |
| 会话冷启动 | <1s(cache) | **12-28s**(24-55k ÷ 2k) |
| compaction 步(700k 重算) | 30-96s | **~6 分钟** ← 本地最痛的点 |
| 全期 decode 挂钟 | 25.6h | 40.1h(慢 1.6×) |
| 最大会话内存 | — | KV 108GB + 权重 142GB = **250GB,顶满 256GB 卡线** |

结论修正:真实负载(小冷启动+微增量+周期 compaction)下,本地稳态轮次
反而比云端快;真正的三个坑是 compaction 步、decode 总时长 +56%、
峰值会话内存卡线(且多会话并行时 KV 累计,2-3 个大会话即满)。
